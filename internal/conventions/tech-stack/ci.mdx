## Test entrypoint

Every Wywy repository **MUST** have a root-level `test.sh` script as the sole entrypoint for running tests. This is the only way to run tests — direct invocation of test runners (`pytest`, `bats`, `valgrind`, etc.) is not permitted. All CI workflows, `ci.sh`, and developer workflows use `test.sh`.

The `test.sh` script is responsible for:

- Starting all required services **if the suite needs them** — the mechanism is repo-specific (see [Service lifecycle](#service-lifecycle))
- Running test suites
- Collecting exit codes from all test suites
- Tearing down any services it started
- Exiting with a non-zero code if **any** test suite failed

### Test suites and the entrypoint router

A repo may have more than one test suite — for example a fast `smoke` suite for pre-commit/push and a heavier `deployment`/staging suite that requires live infrastructure.

- **Single suite:** `test.sh` runs it directly.
- **Multiple suites:** `test.sh` becomes a **thin entrypoint router**. It contains no test logic itself — it maps a suite name (or a default) to a per-suite script under `scripts/tests/**` and delegates. Each suite script is readable and independently runnable; `test.sh` merely picks one and aggregates exit codes.

The rule that keeps this from becoming a monolith: **`test.sh` dispatches, suite scripts do the work.**

Example shape:

```text
test.sh
scripts/tests/
  smoke.sh
  unit.sh
  deployment.sh
```

```bash
case "${1:-smoke}" in
  smoke)      scripts/tests/smoke.sh ;;
  unit)       scripts/tests/unit.sh ;;
  deployment) scripts/tests/deployment.sh ;;
  *) echo "Usage: $0 [suite]" >&2; exit 1 ;;
esac
```

## Script hardening

`test.sh` **MUST** be resilient against symlinks and callable from any working directory on the machine.

### Symlink resolution

Use `${BASH_SOURCE[0]}` (not `$0`) to resolve the script's own location:

```bash
SCRIPT_DIR="$(dirname "$(readlink -f "${BASH_SOURCE[0]}")")"
```

### Working directory independence

`cd` to `SCRIPT_DIR` **immediately after computing it**, so all subsequent relative paths resolve against the repository root regardless of the caller's `$PWD`:

```bash
SCRIPT_DIR="$(dirname "$(readlink -f "${BASH_SOURCE[0]}")")"
cd "$SCRIPT_DIR"
```

This ensures that tool-relative paths (e.g. `docker compose -f`) and local config/log paths resolve correctly regardless of the process CWD.

### Relative paths from SCRIPT_DIR

All paths in `test.sh` — tool file paths, config references, log directory references, and any suite scripts — **MUST** be relative to `SCRIPT_DIR`. Never use absolute paths that embed a specific deployment path.

## Config provisioning

Config files **MUST** be pre-staged before `test.sh` is invoked. `test.sh` **MUST NOT** download or generate config at runtime — no `curl`, `wget`, or equivalent fallback.

Rationale:

- **Security**: The config is a trusted artifact; downloading it from a remote URL at test time introduces a network dependency and a supply-chain risk.
- **Predictability**: A test run should give the same result regardless of network availability or upstream changes.
- **Separation of concerns**: Provisioning is the responsibility of the CI runner (`ci.sh`) or the developer's setup, not the test entrypoint.

Expected config path: `config/ci/config.yml` (relative to `SCRIPT_DIR`).

In CI, the runner downloads and stages config before invoking `test.sh`. Locally, developers run `scripts/install/ci.sh` or equivalent provisioning steps.

## Service lifecycle

`test.sh` is responsible for the lifecycle of any services its suites need: start them, run the suites, tear them down. Cleanup **MUST** happen on any exit path (success, failure, SIGINT, SIGTERM) — use a `trap` on `EXIT`.

The startup mechanism is **repo-specific** — this convention does not mandate a tool. Common patterns:

**docker compose (service repos):**

```bash
COMPOSE="docker compose \
  -f docker/docker-compose.base.yml \
  -f docker/docker-compose.test.yml"
```

**KinD or similar (K8s control repos)** — pattern coming soon.

**No services (control/ops repos):** tests target pre-existing infrastructure (clusters, VMs); `test.sh` starts nothing and has nothing to tear down.

## Error handling

`test.sh` **MUST** use `set -euo pipefail` (standard bash convention).

If service startup fails, the script **MUST** dump the service logs and exit non-zero, so CI can surface the failure reason without a separate log-collection step.

## Exit codes

`test.sh` **MUST** exit 0 if all test suites passed, non-zero if any suite failed. Aggregate exit codes from all suites — do not short-circuit on the first failure.

## Assertion style

Test assertions are governed by the [Testing Conventions](../testing.mdx): **no raw string matching** — parse structured output (YAML, JSON, dotenv) and assert on fields. The dotenv exact-key extraction (`sed -n 's/^KEY=//p'`) is the sanctioned form for line-oriented KEY=VALUE formats.
