> **Cross-cutting** — applies to all services regardless of language.

## Consolidation

All configuration values that could vary across deployments or environments **MUST** live in the control repo (`/etc/Wywy-Website-Control/config/`) and be loaded via env files, YAML config, or Docker secrets. Never embed an environment-dependent value directly in application code or service-level `.env` files.

The only permitted exception is values that nobody could reasonably want to change — these may be hard-coded.

## Environment files

### Location

- Per-service env files: `config/<service>/.env` (production) and `config/<service>/.env.dev` (development overrides).
- Universal env files: `config/.env` and `config/.env.dev`.
- Service-specific env files override universal ones.

### Format

`KEY=VALUE` format, no `export` prefix. Comments use `#`.

```bash
# START - Sync app
DATABASE_HOST=postgres
POSTGRES_USER=postgres
BACKUP_HOST=sshbackup.ericzhu.me
# END - Sync app
```

### Override pattern

`.env` defines the production defaults. `.env.dev` overrides only the values that differ for development. Never duplicate all values — `.env.dev` contains only the delta.

### Priority

```
service .env.dev > service .env > universal .env.dev > universal .env
```

### Value conventions

- Booleans: `TRUE`/`FALSE` (uppercase).
- Numeric values: unquoted (`AGENTIC_API_PORT=2524`).
- String values: unquoted (`BACKUP_HOST=...`).
- `###################################################################################` for section separators.

### Hostname convention

**Never use a specific machine hostname as a default value** in `.env` files, `.env.example` templates, or any configuration template committed to the repo. Use `localhost` or an empty value (`HOST=`) as the placeholder instead.

✅ **Do this:**

```bash
# config/.env.example
AGENTIC_API_HOST=localhost
BACKUP_HOST=
PBS_HOST=
```

❌ **Don't do this:**

```bash
# config/.env.example
AGENTIC_API_HOST=my-dev-machine
BACKUP_HOST=my-backup-machine-1
PBS_HOST=my-backup-machine-2
```

The actual hostname values belong in the deployed `.env` file on each machine, not in the example templates. This keeps templates portable and prevents accidental hostname leakage into CI or test environments.

### Port convention

**Standard service ports are constants, not configuration.** Cluster DNS abstracts the hostname (pods reach the DB as `postgres`, not as an IP), so the only thing that varies about an endpoint is the host — the port is fixed by the service protocol. Hard-code well-known ports (e.g. PostgreSQL `5432`) wherever they are consumed: k8s manifests, scripts, and templates. Never add a `DATABASE_PORT`-style key to env files or the network source.

✅ **Do this:**

```yaml
# k8s manifest
ports:
  - port: 5432
```

❌ **Don't do this:**

```bash
# config/.env
DATABASE_PORT=5432
```

Ports that are genuinely deployment-specific (custom services, agentic API ports, CI ports) remain configuration — the hard-coding exception covers only well-known service defaults.

## Template placeholders

Two notations, split by file type:

### `{{NAME}}` — default (cloud-init scripts, config templates)

Committed template files (cloud-init snippets, `config/db/*`, `*.template`) mark substitution points with `{{NAME}}`:

- `{{NAME}}` appears **only on rule/data lines — never in comments**.
- Comments and documentation reference placeholders as `<NAME>` (angle brackets); this prose form is never substituted.
- Renderers must be **comment-aware**: lines starting with `#` (after optional whitespace) pass through untouched.
- Leftover-placeholder guards scan **non-comment lines** for `{{` and fail the render if any survive.

✅ **Do this:**

```apache
# Calico masquerades pod -> LAN traffic to the node IP, so postgres sees
# the worker IP, never the pod CIDR (<K8S_WORKER_IPS>).
{{K8S_WORKER_IPS}}
```

❌ **Don't do this** — angle-bracket tokens get confused with comment references, and `{{NAME}}` inside a comment gets expanded by a non-comment-aware renderer (or trips the leftover guard):

```apache
# <K8S_WORKER_IPS> is expanded below
<K8S_WORKER_IPS>
```

### `<NAME>` — Proxmox preseed files

`scripts/install/preseeds/proxmox/preseed.cfg` uses `<tag>` tokens (`<hostname>`, `<target_disk>`, `<netiface>`, `<extrapackages>`), substituted by `build-proxmox-iso.sh` via `sed`. This is the established preseed notation — **do not introduce `{{}}` in preseed files**. The preseed's comments reference the same `<tag>` form; that is the token notation there, not a comment-prose convention.

### In use

- `{{NAME}}`: `scripts/proxmox/vm/cloud-init/database-vm.yaml.template` (`{{BOOTSTRAP_B64}}`, `{{PGDG_KEY_B64}}`), `k8s-worker.yaml.template` (`{{NODE_ROLE}}`), `config/db/pg_hba.conf` (`{{K8S_WORKER_IPS}}`, `{{K8S_POD_CIDR}}`). Renderers: `scripts/proxmox/vm/db/update-pg-hba.sh` (comment-aware awk) and `scripts/proxmox/vm/db/create-template.sh` (sed — safe only because comments use `<NAME>`).
- `<NAME>`: `scripts/install/preseeds/proxmox/preseed.cfg`, rendered by `build-proxmox-iso.sh`.

## YAML config

### Root config

`config/config.yml` — site-wide configuration:

```yaml
websiteTitle: "Wywy Website"
websiteIcon: "favicon.svg"

data:
  - dbname: main
    tableName: entries
    entrytype: entry
    datatype: number
```

- `.yml` extension (not `.yaml`).
- camelCase keys for human-readable config fields.
- API-facing fields (db names, table names, column names) should use `lower_snake_case` (see [`naming.mdx`](../../naming.mdx)).

### Test config

`config/test_config.yml` — minimal subset for test environments.

## Pipeline config

### Location

`config/agentic/pipeline.yml`

### Schema

```yaml
defaults:
  timeout_seconds: 600
  max_retries: 3
  max_iterations: 5
  retry_backoff: [30, 60, 120]
  test_timeout_seconds: 60

stages:
  coder:
    timeout_seconds: 1200
```

- All timeouts in seconds.
- All values have documented defaults.
- Stage-specific overrides override `defaults`.

### Env var overrides

Environment variables override YAML config values:

```
PIPELINE_TIMEOUT_SECONDS=900
```

Env var names are `PIPELINE_<YAML_KEY>_<YAML_SUBKEY>` uppercased.

## Loading config

Docker Compose loads env files via `--env-file`:

```bash
docker compose \
  -f docker/docker-compose.base.yml \
  -f docker/docker-compose.dev.yml \
  --env-file /etc/Wywy-Website-Control/config/cache/.env.cache.dev \
  up --build
```

Compose files reference config via environment variables — never hardcode paths or values.
