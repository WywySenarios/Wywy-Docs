> Cross-language rules for writing tests in Wywy repositories. Applies to every test file in every repo, regardless of language or runner: shell (`bats`), Python (`pytest`), Go (`testing`), C, and anything else.
>
> Every test is exactly one of three types: behavioural, schema, or performance.

## Test types

| Type        | Subject            | What it proves                                               |
| ----------- | ------------------ | ------------------------------------------------------------ |
| Behavioural | The code           | Controlled input produces the declared output or side effect |
| Schema      | A declared schema  | A committed input matches it, and invalid input is rejected  |
| Performance | Time and resources | Bounds under load                                            |

Every test must fit exactly one type. A test that fits none is an anti-pattern: delete, split, or convert it to the type it should have been.

Note: there are some VERY VERY VERY rare exceptions externally, including chaos testing. As for the moment, no wywy repo shall contain one of these tests.

### Convention exceptions

Every rule in this document is the default. An exception MUST be explicit in the test and in review.

- Mark the site with `CONVENTION EXCEPTION(<rule>): <reason>` in the language's comment syntax, inline or immediately above the assertion or helper.
- Configuration presence is never eligible for an ad-hoc exception. Validate against the schema; if no schema exists, add one.
- An unmarked exception is a defect. Reviewers and agents reject it.
- Do not declare a blanket exception for a file or suite; each site is marked.

Not exceptions: a parser or serializer test is behavioural; schema validation is a schema test; a plaintext-leak guard is an assertion mechanic.

An exception must explain why the rule's rationale does not apply to this product.

## Behavioural tests

A behavioural test tests runtime behaviour by giving code controlled input and asserting the declared output or side effect.
Each test crosses should verify one interface (i.e. cross one boundary).

A behavioural test should define the expected input and outcome as literal constants (e.g. `INPUT_TOKEN = "ex-token"`, `EXPECTED_RESPONSE = "ex-token-ok"`).
They must not be computed at test-time/run-time.
Mocks and injected seams supply every external value: config, files, database, environment, network, clock, randomness, and paths.

Assert on the code's output, not its source.
Compare scalars directly.
Parse structured output with the format's real parser and assert typed fields; a fixture is data, not an oracle, and a mock's configured return value is not the subject.
Compare fields, not whole generated documents, unless exact bytes are the product.

In the case the code gives structured output, you might need to use parsing libraries. Some common examples include:

| Format    | Use                                                              | Never                  |
| --------- | ---------------------------------------------------------------- | ---------------------- |
| YAML      | `yq`, `yaml.safe_load`, `gopkg.in/yaml.v3`, libyaml              | `grep 'kind: Service'` |
| JSON      | `jq`, `json.loads`, `encoding/json` into a struct, jansson       | `grep '"port": 5432'`  |
| XML       | `xml.etree.ElementTree`, `encoding/xml`, libxml2                 | substring match        |
| KEY=VALUE | exact-key extraction (`sed -n 's/^KEY=//p'`, split on first `=`) | `grep 'KEY='`          |
| CSV       | the format's reader; assert fields                               | `grep -c` on rows      |

For line-oriented KEY=VALUE, exact-key extraction is field extraction, not raw string matching. If the format has a parser, scanning it is a defect. Strip comments before reading file content. Source-text checks are a last resort; a plaintext-leak guard is a security check, not a value assertion.

Values and fixtures are synthetic and named per [`naming.mdx`](naming.mdx#example-and-mock-values) (`ex-token`, `ex-user@example.com`).
A behavioural test that reads real data to assert on it is data exfiltration, not a test.

Tests should be reproducible. That means we shouldn't copy the ambient environment into a subprocess or exfiltrate secrets or runtime information.

Behavioural tests do not test repository transitions. They do not test configuration, either.

### Common mistakes

- Asserting on unparsed output: `grep`, `strings.Contains`, `assert "x" in output`.
- Asserting containment in parsed data: `assert "key" in parsed`.
- Computing the expected value or calling production code as the oracle.
- Reading a real file, production path, or ambient environment in a behavioural test.
- Testing a migration, active or completed.
- Asserting a constant or key exists in a configuration file.
- Testing a script or a test runner.
- Mixing in schema validation or performance timing.

## Schema tests

A schema test proves that a committed configuration conforms to a declared schema.
Every committed configuration file (env, YAML/JSON, service config) MUST have a schema and MUST be validated against it in a configuration schema test suite.

External libraries are recommended.
If the repository's language lacks one, include validation code from another language and a schema validation suite.
For example, if the repository is written in C, it would be a good idea to set up a Python environment to run schema validation with Pydantic.

An example of a good test that verifies that configuration follows the schema:

```python
jsonschema.validate(instance=data, schema=schema)
with pytest.raises(jsonschema.ValidationError):
    jsonschema.validate(instance={}, schema=schema)
```

An example of a bad test that overreaches to becoming the schema:

```python
EX_VALUE = "ex-value"
my_config = yaml.safe_load(config_path.read_text())
assert my_config["ex-key"] == EX_VALUE
assert "ex-key2" in my_config
```

### Schema Definitions

Schemas must be defined in files under folders dedicated to schema definitions. For example,

- `schemas/ex.schema.yaml`
- `schemas/ex.ts`

Schemas must be constant (i.e. be optimizable by the compiler if applicable).
Schemas may be defined with Zod, JSONschema, etc.

### Avoiding data exfiltration

Schema tests must operate on real data (committed configuration) in a bounded way to avoid data exfiltration.

Schema tests may never modify configuration.
No configuration may originate from or be populated by testing code or harnesses.

Schema tests must assert that configuration conforms to a schema.
Schema tests never define, restate, or modify any part or whole schema.

Schema tests must not persist anything to the filesystem.

#### Handling encrypted values

Schema tests may never decrypt any value of any sort.
When a schema test must operate on encrypted values, we give it our best try but realize that our capability to test is limited.
Usually this means that the schema should be dumbed down so that it can apply to encrypted values (e.g. key `XXX` must have regex `ENC[yyy]`).

### Common mistakes

- Asserting a value is present (e.g. `data["mykey"] == MYKEY_VALUE`) instead of validating the schema.
- Restating the schema (e.g. allowed keys, types, or configured values) in the test or in comments.
- Copying a committed value into the test file, a fixture, a log, or an artifact.
- Using example values instead of the committed configuration.
- Decrypting a value or requiring a decryption key.
- Grepping the config file.
- Restricting configuration values beyond the schema definition.
- Asserting behaviour the configuration enables (that is a behavioural test).

## Performance tests

No performance-testing conventions exist yet.
The first repository to add performance tests MUST establish them here: what is measured, the threshold, the fixture, the environment, and how flakiness is handled.
Until then, do not add timing or resource assertions to behavioural or schema tests.

### Common mistakes

- A timing or resource assertion inside a behavioural or schema test.
- A performance test committed before the conventions exist.

## Enforcement

Reviewers and agents must reject any test that fits none of the three types, violates these rules, or carries an unmarked exception.
Implementation plans must NOT specify these anti-patterns. Existing violations must be cleaned up. They must not be grandfathered.
