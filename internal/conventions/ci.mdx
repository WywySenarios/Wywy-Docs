> **Language:** Bash — see [`languages/bash.mdx`](languages/bash.mdx).

## Test suites

Every Wywy repository **MUST** organize its tests as executable suite scripts under `scripts/tests/**`, one script per suite. A repo may have a single suite or several — for example a fast `smoke` suite for pre-commit/push and a heavier `deployment`/staging suite that requires live infrastructure.

```text
scripts/tests/
  smoke.sh
  unit.sh
  deployment.sh
```

Each suite script is a **first-class entrypoint** and is independently runnable. It contains everything needed to run that suite, including its own service lifecycle (see [Service lifecycle](#service-lifecycle)). A developer or CI job invokes the suite script directly:

```bash
scripts/tests/unit.sh
```

Direct invocation of test runners (`pytest`, `bats`, `valgrind`, `terraform test`, etc.) is **not permitted**. Run the suite script instead — it exists to fix the invocation, environment, and service setup in one place.

## The `test.sh` aggregator

A root-level `test.sh` **MUST** also exist, but it is **not the sole entrypoint**. It is a **thin aggregator/router** that:

- contains no test logic itself;
- runs a named suite, or every suite when no suite is named;
- aggregates exit codes without short-circuiting on the first failure;
- rejects unknown suite names.

The rule that keeps this from becoming a monolith: **`test.sh` dispatches, suite scripts do the work.** A suite script must never call `test.sh`.

Example `test.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

cd "$(dirname "$(readlink -f "${BASH_SOURCE[0]}")")"

usage() {
	echo "Usage: $0 [suite|all]" >&2
	exit 1
}

suite="${1:-all}"

if [ "$suite" = all ]; then
	status=0
	for script in scripts/tests/*.sh; do
		"$script" || status=1
	done
	exit "$status"
fi

# Reject anything that is not a plain suite name (no path traversal).
case "$suite" in
	*[!a-z0-9-]*) usage ;;
esac

script="scripts/tests/${suite}.sh"
[ -x "$script" ] || usage
exec "$script"
```

## Script hardening

`test.sh` and **every suite script** under `scripts/tests/**` **MUST** be resilient against symlinks and callable from any working directory on the machine.

### Symlink resolution

Use `${BASH_SOURCE[0]}` (not `$0`) to resolve the script's own location. `test.sh` lives at the repository root; a suite script lives two levels down, so its repository root is two directories up:

```bash
# test.sh
REPO_ROOT="$(dirname "$(readlink -f "${BASH_SOURCE[0]}")")"

# scripts/tests/<suite>.sh
REPO_ROOT="$(readlink -f "$(dirname "${BASH_SOURCE[0]}")/../..")"
```

### Working directory independence

`cd` to `REPO_ROOT` **immediately after computing it**, so all subsequent relative paths resolve against the repository root regardless of the caller's `$PWD`:

```bash
cd "$REPO_ROOT"
```

This ensures that tool-relative paths (e.g. `docker compose -f`) and local config/log paths resolve correctly regardless of the process CWD.

### Relative paths from REPO_ROOT

All paths in `test.sh` and in every suite script — tool file paths, config references, log directory references, and paths to other scripts — **MUST** be relative to `REPO_ROOT`. Never use absolute paths that embed a specific deployment path.

## Config provisioning

Config files **MUST** be pre-staged before any suite is invoked. Neither `test.sh` nor a suite script may download or generate config at runtime — no `curl`, `wget`, or equivalent fallback.

Rationale:

- **Security**: The config is a trusted artifact; downloading it from a remote URL at test time introduces a network dependency and a supply-chain risk.
- **Predictability**: A test run should give the same result regardless of network availability or upstream changes.
- **Separation of concerns**: Provisioning is the responsibility of the CI runner (`ci.sh`) or the developer's setup, not the test entrypoints.

Expected config path: `config/ci/config.yml` (relative to `REPO_ROOT`).

In CI, the runner downloads and stages config before invoking a suite script or `test.sh`. Locally, developers run `scripts/install/ci.sh` or equivalent provisioning steps.

## Service lifecycle

Each suite script is responsible for the lifecycle of any services **its own tests** need: start them, run the tests, tear them down. `test.sh` is a router and **MUST NOT** start or tear down services.

Cleanup **MUST** happen on any exit path (success, failure, SIGINT, SIGTERM) — use a `trap` on `EXIT`.

If service startup fails, the suite script **MUST** dump the service logs and exit non-zero, so CI can surface the failure reason without a separate log-collection step.

The startup mechanism is **repo-specific** — this convention does not mandate a tool. Common patterns:

**docker compose (service repos):**

```bash
COMPOSE="docker compose \
  -f docker/docker-compose.base.yml \
  -f docker/docker-compose.test.yml"
```

**KinD or similar (K8s control repos)** — pattern coming soon.

**No services (control/ops repos):** tests target pre-existing infrastructure (clusters, VMs); the suite scripts start nothing and have nothing to tear down.

## Error handling

`test.sh` and every suite script **MUST** use `set -euo pipefail` (standard bash convention).

## Exit codes

Each suite script **MUST** exit 0 if its suite passed and non-zero if it failed. `test.sh` **MUST** exit 0 if every suite it ran passed, non-zero if any suite failed. It MUST aggregate exit codes from all suites — do not short-circuit on the first failure.

## Assertion style

Test assertions are governed by the [Testing Conventions](testing.mdx): **no raw string matching** — parse structured output (YAML, JSON, dotenv) and assert on fields. The dotenv exact-key extraction (`sed -n 's/^KEY=//p'`) is the sanctioned form for line-oriented KEY=VALUE formats.
