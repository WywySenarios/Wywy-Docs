## Overview

Wywy CI runs on self-hosted GitHub Actions runners organized into **capability pools**. This document defines the conventions repositories must follow when authoring workflow files. It does not describe what is currently deployed — the deployed layout lives in the control repo at `k8s/dev/github-runner/README.md`.

## Label conventions

Every job in `.github/workflows/*.yml` must set `runs-on:` to a label set that is a subset of exactly one deployed pool's runner labels.

| Label         | Meaning                                  |
| ------------- | ---------------------------------------- |
| `self-hosted` | Distinguishes from GitHub-hosted runners |
| `<org-label>` | Organizational namespace (e.g. `wywy`)   |
| `dind`        | Job needs Docker-in-Docker               |
| `kind`        | Job creates a throwaway KinD cluster     |

Every job must include the org label (`wywy`). `self-hosted` is always present in deployed pools but jobs may omit it and rely on the org label alone (`runs-on: [wywy]`).

## Pool types

Three pool types exist; a repo deploys only the pools it has jobs for. A job's `runs-on` set must match exactly one pool:

| Pool    | Runner labels           | Valid `runs-on`             |
| ------- | ----------------------- | --------------------------- |
| generic | `self-hosted,wywy`      | `[self-hosted, wywy]`       |
| dind    | `self-hosted,wywy,dind` | `[self-hosted, wywy, dind]` |
| kind    | `self-hosted,wywy,kind` | `[self-hosted, wywy, kind]` |

Rules:

- **Do not combine `dind` and `kind` in one job.** No pool carries both labels — such a job matches no pool and queues forever.
- **KinD jobs use the `kind` pool only.** The kind pool bundles the DinD daemon, so a KinD job must not also request `dind`.
- A job's `runs-on` must be a subset of the pool's labels; requesting a label no deployed pool carries means the job never runs.

## Choosing a pool

| Job needs                                            | Use pool | `runs-on`                   |
| ---------------------------------------------------- | -------- | --------------------------- |
| Nothing special (no declared capability)             | generic  | `[self-hosted, wywy]`       |
| `docker compose` / multi-container integration tests | dind     | `[self-hosted, wywy, dind]` |
| `kind create cluster` + `kubectl`                    | kind     | `[self-hosted, wywy, kind]` |

A repo with no deployed pool matching its jobs must have that pool added to the infrastructure (see `k8s/dev/github-runner/README.md` in the control repo) before the workflow will run.

## Scaling semantics (why pools must be exact)

Each pool's KEDA trigger labels equal the pool's own runner labels. KEDA scales a pool only for queued jobs whose `runs-on` matches that pool — so a job that matches no pool is never dispatched and never triggers a scale-up.
